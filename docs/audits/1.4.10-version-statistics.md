# Impuls 1.4.10 version-statistics privacy and security review

Date: 18 August 2026
Scope: GitHub Issue #40, Settings redesign, release download reporting,
`VersionTelemetryService`, and the self-hosted collector.

## Result

The release adds a third explicit network boundary without weakening the two
existing ones. Version statistics are inert unless both conditions hold:

1. the user changes the dedicated consent from `unknown` to `allowed`; and
2. the release build contains an owner-configured HTTPS endpoint whose exact
   path is `/v1/heartbeat`.

`unknown` is the default for new and upgraded users. The source tree contains no
production collector URL. Therefore installing 1.4.10 alone cannot begin
sending statistics.

## Client data flow

The only encoded fields are pinned by `VersionTelemetryService.Payload` and its
`CodingKeys`:

```json
{
  "schema": 1,
  "installation_id": "random-uuid",
  "app_version": "1.4.10",
  "previous_version": "1.4.9"
}
```

`previous_version` is optional. It is written only after the application has
observed one valid running version and later observes another. Version 1.4.9 did
not persist a running-version marker, so 1.4.10 deliberately does not infer that
every first launch is an upgrade from 1.4.9. A real observed transition is sent
once after a successful `204` response.

The installation UUID comes from Foundation's random UUID generator. A
device-only Keychain generic-password item keeps it stable. No serial number,
UDID, Bluetooth/MAC address, host name, Apple ID, account value, device name, or
other hardware/user input is read by this service. Consent, last attempt, and
version-transition state are separate UserDefaults keys and are not part of an
exported settings backup.

The attempt timestamp is committed before `URLSession` begins. This means a
timeout or failing server cannot turn every relaunch into another request and
exceed the one-attempt-per-24-hours promise. Errors reduce to a local `.failed`
result and never enter the panel, startup, or another service.

## Collector boundary

`Collector/version-statistics/collector.py` uses only the Python standard
library. It accepts only `POST /v1/heartbeat`, `application/json`, and at most
2 KiB. Validation rejects missing, duplicate, unknown, wrongly typed, oversized,
or malformed fields and requires a canonical version-4 UUID. A process-local
rate limiter uses an HMAC of the peer address; the address is not persisted.

Before SQLite, the raw UUID becomes HMAC-SHA256 with an owner secret of at least
32 bytes. SQLite stores:

- installation HMAC;
- `first_seen`;
- `last_seen`;
- `current_version`;
- optional `previous_version`;
- deduplicated transition rows keyed by the same HMAC.

The handler disables its access log. Deployment documentation requires TLS at a
reverse proxy and requires access logging for the heartbeat route to be disabled
or stripped of IP/User-Agent. The owner report is a local CLI rather than a
public summary endpoint. Its human and JSON outputs both state that the result
covers consenting installations, not all Impuls users.

## Negative data inventory

Neither client schema nor collector accepts clipboard content, notes, snippets,
file names or paths, calendar data, playback data, device names, serial numbers,
UDIDs, hardware identifiers, installed-app lists, logs, IP address, or
User-Agent as a product field. The installation UUID is a persistent pseudonym,
so the UI and policy do not describe the statistic as fully anonymous.

## Network separation

- `UpdateService.swift`: user-consented, signed GitHub/Sparkle update channel.
- `WebMusicPlayer.swift`: official provider site after **Open Web Player**.
- `VersionTelemetryService.swift`: separately consented, version-only heartbeat
  to an optional owner-configured endpoint.

CI bans networking APIs in every other source file, pins the telemetry endpoint
path and payload field names, and launches a build with no collector endpoint
under `CI=true` to prove that startup opens no internet socket.

## Tests and operational checks

Automated coverage includes zero requests for `unknown` and `denied`, exact
allow-listed JSON for `allowed`, 24-hour throttling including failure, timeout
isolation, endpoint validation, stable random Keychain UUID, one-time version
transition, 1.4.9 settings preservation, Settings sidebar persistence, strict
collector validation, raw-ID absence from SQLite, rate limiting, owner-report
scope wording, and GitHub asset download-count semantics.

Release acceptance still requires the full release test suite, bundle/signature
verification, RU/EN localization checks, static network-boundary audit, and a
launch smoke test. A production collector deployment and real traffic cannot be
verified until the owner chooses a hostname, secret storage, TLS proxy, backup,
and retention policy; the application endpoint must remain unset until then.

## Follow-up: hourly heartbeat

Date: 19 August 2026

The 24-hour statements above describe the 1.4.10 release as originally audited.
The next client release changes only the attempt interval to one hour
(`60 * 60`). Consent, the exact HTTPS `/v1/heartbeat` endpoint, the payload
allow-list, UUID handling, HMAC storage, and failure behaviour remain unchanged.
Dedicated tests cover a successful first attempt, throttling at 59 minutes 59
seconds, a second attempt exactly at one hour, and the same throttle after a
failed request. The release and build workflow literal checks are updated with
the same interval.

## Follow-up: owner dashboard release-version synchronization

Date: 19 August 2026

The private owner dashboard now obtains its latest-version label only from the
fixed, unauthenticated GitHub endpoint
`https://api.github.com/repos/TumanovNV/impuls/releases/latest`. This is a
server-side operational request, not a new client network boundary: the
rendered page has no external assets or JavaScript, and no installation data,
collector secret, GitHub token, client address or telemetry payload is supplied
to GitHub.

The resolver rejects redirects, non-200 responses, bodies over 32 KiB, draft or
prerelease responses, non-`v` tags and invalid release versions. It atomically
persists only a validated version and fetch timestamp in a mode-`0600` local
cache. On an unavailable or invalid GitHub response it keeps the latest cached
value; before the first successful refresh it retains the owner-configured
bootstrap release. Tests cover validation, durable recovery after an outage and
private dashboard refresh without a browser-side dependency.

## Follow-up: version-aware attempt throttling and periodic in-process heartbeat

Date: 21 August 2026

A real regression was found: `sendHeartbeatIfNeeded()` was called exactly once,
~2 seconds after launch, and its once-per-hour throttle was keyed only on a
timestamp. A Mac that attempted a heartbeat on version N and updated to
version N+1 minutes later would have that first N+1 launch silently throttled
by N's still-cooling-down hour, and since nothing retried later in the same
session, the dashboard kept counting that Mac as version N until a person
happened to relaunch the app again after the hour passed.

Two independent, additive changes fix this without touching the payload or
consent model:

1. **Version-aware throttle.** `VersionTelemetryService` now also persists
   `versionStatistics.lastAttemptVersion.v1` alongside the existing attempt
   timestamp, both written before every attempt (success or failure). The
   throttle only applies when the *current* app version matches the version
   of the *last* attempt. A different app version — including a fresh 1.4.14
   install whose defaults predate this key entirely — is not held back by an
   older version's cooldown and gets one immediate attempt. A version that
   keeps failing is still limited to one attempt per hour, because both keys
   are written together on every attempt regardless of outcome. No new
   migration code was needed: `defaults.string(forKey:)` for a key that was
   never written simply returns `nil`, which never equals the current version
   string.
2. **Periodic in-process scheduler.** A new `VersionTelemetryScheduler`
   (`@MainActor`, one `Timer`, `1 h` interval with `interval / 4` tolerance)
   proposes an attempt roughly hourly for as long as the app keeps running,
   started right after the existing `+2 s` first attempt and stopped in
   `applicationWillTerminate`. It carries no policy of its own — every
   proposal still goes through `VersionTelemetryService.sendHeartbeatIfNeeded()`,
   which is the only thing that decides whether a proposal becomes a request.
   An update that lands mid-session, or a first attempt that was throttled,
   now gets a real subsequent chance without requiring a second manual
   relaunch.

Unchanged: consent model, endpoint validation, the exact `/v1/heartbeat`
route, the payload allow-list (`schema`, `installation_id`, `app_version`,
optional `previous_version`), redirect rejection, and the once-per-hour
ceiling for a given version. `pending_previous_version` continues to survive
a failed attempt and is cleared only after a successful `204`.

Separately, the private dashboard's GitHub latest-release refresh default
moved from 3600 to 300 seconds (still constrained to 300–86400 by
`IMPULS_DASHBOARD_GITHUB_REFRESH_INTERVAL`), so the "latest published
version" label does not lag a real release by up to an hour. This is a
server-side scheduling change on the owner-only dashboard process; it adds no
client network request and does not change what the client sends. The
dashboard's own report query already reads SQLite live on every request —
there is no additional cache of `installations_by_app_version` to go stale.

Tests: `VersionTelemetryServiceTests.swift` (version-aware throttle, same-version
throttling, exact-hour boundary, failure-then-relaunch throttling, migration
from a pre-1.4.14 install, pending-previous-version survival/clearing,
missing-endpoint zero-request), `VersionTelemetrySchedulerTests.swift`
(idempotent start/stop, ticks respecting the service's own throttle),
`test_version_statistics_dashboard.py` (default refresh interval, dashboard
reflecting a newly recorded heartbeat without a server restart).
