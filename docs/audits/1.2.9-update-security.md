# Impuls 1.2.9 update-channel review

## Scope

This review covers the transition from the custom release-page checker to
Sparkle 2.9.5 and the production release pipeline that creates the appcast and
update ZIP.

## Trust model

- `Package.swift` pins Sparkle to 2.9.5 and `Package.resolved` pins revision
  `79bc9e872948e47877e76f194cb0c8e0412b0b90`.
- `SUPublicEDKey` is embedded in the application; the corresponding private seed
  is not stored in the repository or release assets.
- `SUVerifyUpdateBeforeExtraction` and `SURequireSignedFeed` are enabled.
- signed-feed failures have no expiry fallback.
- appcast archive URLs are generated only for a versioned release in
  `TumanovNV/impuls`.

## Privacy and consent

- automatic checks start only after the user has allowed them;
- the prior 1.2.8 decision is migrated once and the obsolete preference is
  removed;
- system profiling, automatic download, and unattended installation are off;
- content from the clipboard, notes, files, calendar, media, and local stores is
  never added to an update request.

## Packaging

- the framework is copied with symlinks preserved;
- the executable has an explicit app-bundle framework rpath;
- archives are created with `ditto --keepParent` and are extracted and verified
  in CI;
- production CI signs and verifies the appcast with Sparkle's tools, publishes
  DMG and ZIP checksums, and creates the release only after successful tests.

## Remaining limitation

The public application is ad-hoc signed until Developer ID is issued. First
installation still requires manual Gatekeeper approval. The ad-hoc entitlement
that disables Library Validation is isolated from the Developer ID signing path.
The first real end-to-end update must be verified with 1.2.9 → 1.2.10 on a Mac.
